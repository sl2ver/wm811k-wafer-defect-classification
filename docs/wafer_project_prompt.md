# 웨이퍼 맵 결함 패턴 분류 프로젝트 — Claude Code 시작 프롬프트

아래 전체를 Claude Code 첫 메시지로 붙여넣는다.

---

## 0. 너의 역할과 나의 역할

나는 이진성, 전기정보공학 석사과정(RF/EMC 전공)이다. 반도체 제조 데이터는 처음 다룬다.
이 프로젝트는 24시간 안에 끝내는 개인 해커톤 연습이고, 결과물과 **작업 과정 기록** 둘 다 포트폴리오로 쓴다.

역할은 이렇게 나눈다.

- **내가 정한다**: 문제 정의, 성공 기준, 데이터 분할 방식, 모델 선택, 무엇을 버릴지
- **네가 한다**: 데이터 탐색, 코드 구현, 실험 실행, 결과 정리, 선택지와 근거 제시
- **판단이 필요한 지점에서는 멈추고 나에게 묻는다.** 선택지 2~3개와 각각의 장단점을 제시하고, 추천이 있으면 이유와 함께 밝힌다. 조용히 하나를 골라 진행하지 않는다.
- 내 지시가 틀렸다고 생각하면 **반대 의견임을 명시하고 근거를 댄다.** 그대로 따르지 않는다.

## 1. 목표

공개 웨이퍼 맵 데이터셋 **WM-811K**(LSWMD)로 결함 패턴(Center, Donut, Edge-Loc, Edge-Ring, Loc, Near-full, Random, Scratch, none)을 자동 분류하는 파이프라인을 만들고, 결과를 한눈에 볼 수 있는 대시보드까지 완성한다.

최종 산출물:

1. 재현 가능한 파이프라인 (데이터 로드 → 전처리 → 학습 → 평가, 명령 한 줄로 재실행)
2. 결과 대시보드 (Streamlit): 클래스별 성능, 혼동 행렬, 오분류 사례의 실제 웨이퍼 맵
3. 기록 파일 4개 (아래 3절)

## 2. 작업 원칙

- **숫자는 실행 결과에서만 가져온다.** 추정치를 결과처럼 쓰지 않는다. 결과를 적을 때는 어떤 스크립트·어떤 설정에서 나온 값인지 함께 적는다.
- **정확도(accuracy) 하나로 판단하지 않는다.** 이 데이터는 클래스 불균형이 극심하다. 매크로 F1, 클래스별 재현율(recall), 혼동 행렬을 기본 지표로 한다.
- **좋은 결과일수록 의심한다.** 성능이 예상보다 높으면 다음을 먼저 점검하고 결과를 보고한다:
  - 학습/평가 데이터 사이의 중복 또는 누수 (같은 로트(lot)의 웨이퍼가 양쪽에 섞였는지)
  - 라벨 없는 샘플이 섞였는지
  - 라벨을 무작위로 섞었을 때 성능이 우연 수준으로 떨어지는지 (셔플 라벨 테스트)
- **베이스라인부터.** 복잡한 모델 전에 단순 기준(다수 클래스 예측, 간단한 특징 + 로지스틱/랜덤포레스트)을 먼저 만들어 비교 기준으로 삼는다.
- **최소한으로.** 요청하지 않은 기능, 한 번 쓰는 추상화, 필요 없는 설정 옵션을 만들지 않는다.
- 각 단계가 끝나면 **확인 방법**(무엇을 실행해 무엇을 보면 되는지)을 제시한다.

## 3. 기록 파일 — 처음부터 만들고 계속 채운다

프로젝트 루트에 아래 4개를 만든다. 이 기록이 포트폴리오의 원재료이므로 빠뜨리지 않는다.

### `PLAN.md`
- 문제 정의, 성공 기준(숫자), 단계별 계획과 각 단계의 확인 방법
- 계획이 바뀌면 지우지 말고 **변경 이력**으로 남긴다 (무엇을, 왜 바꿨는지)

### `LOG.md`
시간순 작업 일지. 각 항목에 다음을 적는다:
- 시각
- **내가 준 지시 원문** (요약하지 말고 그대로)
- 네가 한 일과 결과 (수치 포함)
- 판단 지점에서 내가 고른 선택지와 이유
- **오류 기록**: 네 코드나 판단이 틀렸던 경우, 누가(나/너) 어떻게 발견했고 무엇을 바꿨는지. 틀린 것을 숨기지 말고 반드시 남긴다.

### `RESULT.md`
- 최종 수치 (베이스라인 대비 비교표)
- 시도했다가 **버린 것과 버린 이유**
- 남은 한계

### `GLOSSARY.md`
나는 반도체 제조 용어에 익숙하지 않다. 작업 중 등장하는 업계 용어를 쉬운 설명과 함께 정리한다.
- 예: 웨이퍼, 다이(die), 로트(lot), 수율(yield), 웨이퍼 맵, 결함 패턴별 의미와 **주로 어떤 공정 문제를 시사하는지**
- 공정 원인 연결은 확인 가능한 출처가 있을 때만 적고, 출처를 함께 적는다. 확실하지 않으면 "일반적으로 알려진 해석"이라고 표시한다.

## 4. 진행 단계와 체크포인트

각 체크포인트(★)에서는 **반드시 멈추고 나에게 보고한 뒤 지시를 기다린다.**

### 1단계. 환경과 데이터 확보 (목표 ~2시간)
- 파이썬 환경 확인, 필요한 패키지 설치
- WM-811K 데이터 확보 방법을 확인한다. 공개 경로(예: Kaggle `LSWMD.pkl`)와 로그인·용량 등 제약을 조사해 보고한다. **다운로드가 막히면 우회하지 말고 나에게 알린다.**
- 폴더 구조와 기록 파일 4개 생성

★ **체크포인트 1**: 데이터 확보 방법, 용량, 필요한 내 조치를 보고

### 2단계. 데이터 탐색 (목표 ~3시간)
- 전체 샘플 수, 라벨 있는/없는 샘플 수, 클래스별 분포, 웨이퍼 맵 크기 분포, 로트 정보 유무
- 클래스별 대표 웨이퍼 맵을 그림으로 저장
- 데이터에서 발견한 **이상한 점이나 주의할 점**을 목록으로 정리 (예: 크기 불일치, 라벨 오기, 중복)
- GLOSSARY.md에 결함 패턴 9종 정리

★ **체크포인트 2**: 탐색 결과와 함께 다음을 나에게 묻는다
  - 라벨 없는 샘플을 어떻게 다룰지
  - 학습/평가 분할을 무작위로 할지, 로트 단위로 할지 (각각이 무엇을 측정하는지 설명)
  - 'none' 클래스를 포함할지, 결함 웨이퍼만 대상으로 할지
  - 이 결정을 바탕으로 PLAN.md의 성공 기준을 함께 확정

### 3단계. 베이스라인 (목표 ~3시간)
- 다수 클래스 예측 기준
- 간단한 특징(결함 밀도, 영역별 결함 비율 등) + 고전 모델
- 셔플 라벨 테스트
- 결과를 표로 정리

★ **체크포인트 3**: 베이스라인 결과, 가장 헷갈리는 클래스 쌍, 개선 방향 후보 2~3개 제시

### 4단계. 본 모델 (목표 ~7시간)
- 체크포인트 3에서 내가 고른 방향으로 구현 (예: 크기를 맞춘 웨이퍼 맵 입력의 소형 CNN)
- 클래스 불균형 대응 방법을 적용할 경우, 적용 전후를 **같은 평가 데이터**에서 비교
- 누수 점검(2절)을 다시 수행하고 결과를 LOG.md에 기록

★ **체크포인트 4**: 베이스라인 대비 결과표, 오분류 사례 분석(어떤 패턴을 무엇으로 착각했는지, 사람이 봐도 헷갈리는지)

### 5단계. 대시보드 (목표 ~4시간)
- Streamlit 한 페이지:
  - 핵심 수치 요약 (베이스라인 대비)
  - 클래스별 재현율·F1 막대그래프
  - 혼동 행렬
  - 클래스를 고르면 정답/오답 웨이퍼 맵 예시를 보여주는 뷰
- 실행 방법을 README.md에 적는다

★ **체크포인트 5**: 대시보드 스크린샷과 실행 방법 보고

### 6단계. 정리 (목표 ~3시간)
- RESULT.md 완성
- LOG.md에서 **오류 기록만 모은 요약**과 **내가 내린 판단 목록**을 RESULT.md 끝에 붙인다
- 재현 확인: 새 터미널에서 README 순서대로 처음부터 실행해 같은 숫자가 나오는지

★ **체크포인트 6**: 최종 보고

## 5. 보고 방식

- 한국어로 답한다
- 무엇을 왜 했는지 근거와 함께 밝힌다
- 확인이 필요한 사항은 답변 끝에 모아서 제시한다
- 실수했으면 그렇게 말하고, 원인을 밝히고, LOG.md에 기록한다

지금 1단계부터 시작해 줘. 먼저 PLAN.md 초안을 만들고, 데이터 확보 방법을 조사해 체크포인트 1 보고를 해 줘.
